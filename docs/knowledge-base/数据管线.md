rl的数据管线，rollout的时候 可以选择stride=2，保存更多的数据 供给强化学习训练，观测经过vla的得到 rltoken。因为stride=2 没有对应的rltoken。

**本仓库 Stage 2 V1 不使用 stride=2**（2026-09-01 用户锁定）：一次执行长度为 \(C\) 的 chunk 只写入一条 replay transition。stride 子采样与跨 chunk 窗口组装明确未做；见 [`docs/online-rl/stage2_survey.md`](../online-rl/stage2_survey.md)。正式训当前 YAML 是 `num_envs=16`（必须同时设 `reconfigure_every_episodes`）；`--gpu-smoke` 另用并行 ManiSkill 做短资源探测。
${ s_2 \rightarrow \text{Frozen VLA embeddings} \rightarrow \text{RL Token Encoder} \rightarrow z_{\mathrm{rl},2} }$

## PegInsertionSide-v1 视觉观测

用于 SmolVLA SFT 的视觉数据必须通过项目环境
`PegInsertionSideThreeCamera-v1` 重渲染，并且三路相机的 UID、顺序和训练时的
rename map 保持一致：`environment_camera`（全局）、`hand_camera`（腕部）和
`insertion_camera`（红色插入端近景）。相机位置和分辨率由
`configs/vla/peg_insertion_three_cameras.json` 定义；当前目标是每路原始图像
`512×512`，与 SmolVLA 的内部 `512×512` 图像预处理匹配。

在完整重渲染前，用 `scripts/preview_cameras.py` 在存储的专家环境状态上渲染单帧
拼图，覆盖接近、对齐、插入三个阶段。该预览只读取 `trajectory.h5`，不会修改原始
轨迹或现有 LeRobot 数据集。相机配置定稿后，才重放所有 trajectory 并建立新的、
不与原有 `128×128` 数据混用的 LeRobot 数据集。

全量构建使用 `scripts/build_three_camera_lerobot_dataset.py`：它从原始
`trajectory.h5` 逐条恢复保存的环境状态，并先按 trajectory JSON 的 episode seed
重建随机几何；因此状态、动作仍来自原始专家数据，而三个 `512×512` RGB observation
来自当前相机配置。RGB 直接流式编码为 LeRobot MP4，不生成中间 RGB HDF5。构建应先
写入暂存目录 `motionplanning_rgb_pd_joint_pos.rebuild`，验证 episode/frame 数、
三路视频和可加载性后，再原子替换训练数据目录。输出内的 `camera_config.json` 与
`render_manifest.json` 记录精确配置、哈希和所用 episode seed。

2026-08-30 已切换到三路 `512×512` 训练集：本地目录
`data/lerobot/PegInsertionSide-v1/motionplanning_rgb_pd_joint_pos`（1000 episode /
149,055 帧；`environment_camera`、`hand_camera`、`insertion_camera`）。旧两路
`128×128` LeRobot 集（`base_camera` + `hand_camera`）已从本地删除，并在 Hub
`wkal/smolvla-rlt` 上被同一份三路集替换（commit
`6962169243603d7da6e437767af4792c63689cc4`）。训练可用本地 `--dataset.root` 或该
Hub repo。

SFT 入口是 `scripts/train_sft.py`（`scripts/train_sft.sh` 转发到它）。它读取
`configs/vla/smolvla_sft.yaml`，把三路相机 rename 成 smolvla_base 的
`camera1/2/3`，并调用 `lerobot-train`。W&B project 为 `smolvla-rltoken`。
正式 20000 步必须在 AutoDL **网页终端**执行 `bash scripts/train_sft.sh`（脚本会
`nohup setsid` 后台拉起，并把 `ulimit -n` 提到 1048576）。不要从 Cursor agent
启动：agent 会给子进程打上 `ownerAgentId`，大约 20 分钟后 SIGKILL 整棵进程树
（无 Python traceback；从 agent 里 `screen` / `setsid` / `nohup` / 本机 sshd
也逃不掉）。启动器同时检查 Cursor 与 Codex 的环境标记及进程祖先；
`--check` 和短时 `--smoke` 仍允许在 agent shell 中运行。sshd/PAM 默认 soft NOFILE 1024，不抬上限时 16 个 torchcodec worker
会在约 150 step 触顶 `Errno 24 Too many open files`，主进程卡在等 batch，显存
仍占用但 GPU 掉到 P8、功率约 25W。

2026-08-31 的六次 20k 正式启动分别停在 716 / 2504 / 2394 / 164 /
2002 / 1986 step。其中 164-step run 是 NOFILE=1024 导致的解码 worker 失败；
其余运行的主因是 `num_workers=16` 下的容器总内存增长。AutoDL 本地
`autopanel.monitor.db` 记录到：1000-step smoke 已用到 106,582 MB；后两次
正式 run 在 120,061 MB / 120,024 MB 处立即掉回空闲内存，并以
137（SIGKILL）结束。W&B 只显示主训练进程 RSS 约 14.8 GB，没有包含
全部 DataLoader/decoder worker 的 cgroup 聚合用量，因而不能用来排除 cgroup OOM。

默认已从 16 改回 LeRobot 上游默认的 `num_workers=4`。16 worker 时解码只占
单 step 约 4%，因此降低 worker 仍应以 GPU update 为主要瓶颈，同时按 worker
数量显著降低解码器聚合内存。该修复在无 GPU 状态下只做了配置、启动保护
和 CPU preflight 验证；下次有 GPU 时应先跑 `--smoke --steps=1500`，并确认
AutoDL 内存不再向 120 GB 增长，再开正式 20k。

独立风险：最后一次在 agent 修改启动脚本后 79 秒即启动，而旧保护只检查
实际并不存在的 `CURSOR_AGENT`，漏掉了 `CODEX_SESSION_ID` /
`CODEX_THREAD_ID` 等现行标记。启动器现在也会拒绝这些 agent-owned 正式运行；
但对 2026-08-31 后两次 137 的直接证据是约 120 GB 的 cgroup OOM。
无 GPU 时用 `--check` 校验本地数据集与启动命令，不加载模型、不训练。
GPU 冒烟用 `--smoke`（2 步，写入 `outputs/sft/peg_insertion_smoke`，不占正式输出目录）。
视频解码默认 `torchcodec`（conda 环境 `torchcodec==0.7.0`，与 `torch 2.8` 匹配）。
`pyav` 仍是 LeRobot 保底，仅在 torchcodec native 库加载失败时使用。
不要把 `torchcodec` 升到 0.10：该版本对应 torch 2.10，在本机无法加载。

Stage 1 RL Token 用同一份三路 LeRobot 集和同一套 rename。入口
`scripts/train_rltoken.py`：不改写 policy 的 `camera1/2/3`，preprocessor 把数据集
键改成预训练键后再 `prepare_images`。`--checkpoint` 指向 SFT 的
`checkpoints/last/pretrained_model`（不是 `outputs/sft/peg_insertion`）。
CPU `--check` 不加载 VLA。Prefix-only 抽取要 `fill_kv_cache=True`，否则
`cross_attn` 路径会在 expert=`None` 时崩溃。训练按 episode 做 90/10 holdout
（`val_ratio=0.1`，`seed=1000` 可复现；1000 条 demo → 900 train / 100 val），
`val_loss_ro` 与训练共用 masked mean-MSE，不按帧随机切。正式训每次在
`outputs/rl_token/run_YYYYMMDD_HHMMSS/` 下写 checkpoint，不覆盖父目录。`--pressure` 关闭
val、用全量数据测吞吐。2026-09-01 压力记录见
`benchamrk/rlt/pressure_20260901_123758.md`（batch 16–64 均成功，64 的
nvidia 峰值 5253 MiB）。适配进度见 `docs/rltoken-training/`。

2026-08-31 在 4090 上用 `batch_size=32`、`num_workers=16`、`torchcodec`
跑了 1000 step 冒烟（不存 ckpt）。稳态 `data_s≈0.018 s`、`updt_s≈0.48 s`
（加载只占 step 时间约 4%），约 2.0 step/s；显存峰值 **11515 MiB / 24 GB**，
GPU util 中位约 90%。该 run 同时证明 16 worker 过量：容器总内存在
1000 step 已到 106,582 MB。当前正式配置使用 `num_workers=4`，不再使用 16。

用于连续检查时，`scripts/render_camera_videos.py` 会在不修改任何数据的前提下，按
`trajectory.json` 中的 episode seed 重建随机几何并将三路画面拼成 MP4；默认随机抽取
5 条轨迹，抽样 seed 和所用相机配置的 SHA-256 会写入输出目录的
`render_manifest.json`。

需要交互调节时，运行 `scripts/tune_cameras.py`。它固定一个专家轨迹状态，在同一
个已创建的 ManiSkill 场景中实时更新三路相机并返回 RGB：
`environment_camera` 使用世界坐标的位姿与 FOV；`insertion_camera` 挂载在 peg 上，
以红色插入端为局部坐标原点，使用相对于该红端的位姿并随 peg 运动；`hand_camera`
使用相对于 Panda `camera_link` 的局部平移、Roll/Pitch/Yaw 与 FOV。预览脚本先按轨迹
JSON 中记录的 episode seed 重建 box/hole 与 peg 长度的随机几何形状，再设置 HDF5
中存储的状态。
浏览器中的“保存配置”是唯一会写入
`configs/vla/peg_insertion_three_cameras.json` 的操作；在此之前的滑条调整不影响
数据和后续训练。
